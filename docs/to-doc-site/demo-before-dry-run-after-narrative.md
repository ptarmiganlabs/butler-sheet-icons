## What changes on the front page

The front page already tells half the story: a "See it in Action" GIF, then a Before and an After screenshot. Three changes complete it:

### 1. Replace the front-page GIF with a video

`docs/public/images/demo-animated.gif` is 3.5 MB, 1380x623, 1020 frames — a heavy page load with no pause or scrub. Replace it with the WebM/MP4 pair from the demo pipeline (`demo/output/qseow-dry-run.webm` / `.mp4`), which weigh roughly a tenth of that. VitePress renders raw HTML in markdown, so the `![...]` image line becomes:

```html
<video autoplay loop muted playsinline width="1280">
  <source src="/images/qseow-dry-run.webm" type="video/webm" />
  <source src="/images/qseow-dry-run.mp4" type="video/mp4" />
</video>
```

- `muted` + `playsinline` are what allow mobile browsers to autoplay at all; keep all four attributes.
- Both sources: Safari has shipped WebM support for years, but the MP4 fallback costs one file and removes the question.
- The old GIF file is deleted from `docs/public/images/` once nothing references it. A GIF render of the same recording continues to exist in the BSI repo's demo pipeline for the places video cannot go — the GitHub README and social cards.

The recording it replaces also changes character: the old GIF showed a full Cloud thumbnail run; the new one shows the QSEoW **dry run**, which is the better first impression — it shows what the tool will do, in seconds, with the per-sheet plan on screen. The full-length real run remains available as an asciinema cast in the BSI repo for a possible player embed later (issue #1003 part 3, low priority).

### 2. Regenerate the Before / After pair

Replace `docs/public/images/app-overview-before.png` and `app-overview-after.png` with the regenerated pair from `demo/output/panels/` (`app-overview-before.png`, `app-overview-after.png`). These are captured by BSI itself during real runs against the demo app — the same app, the same overview page, with a real thumbnail run in between. That is what makes the pair regenerable on demand instead of a one-off hand grab.

Note on quality: the current pair are hand-made retina grabs (~2314x1266). The regenerated captures are made at the run's own viewport, so compare before publishing; if they are visibly worse, hold this part until issue #735 (dedicated overview capture with its own `deviceScaleFactor`) lands, and say so in the PR. The narrative structure below does not depend on which pair is live.

### 3. Put the dry run between Before and After

Reorder the front-page sections so the story reads **before → plan → after**: the grey overview, then the terminal showing which sheets will get thumbnails and why, then the same overview with thumbnails. Concretely: move the (now video) "See it in Action" section between the Before and After images, retitling to make the three-step story explicit, e.g.:

1. **Before** — every sheet grey (`app-overview-before.png`)
2. **The plan** — the dry run video: what would change, and why
3. **After** — the same overview, now with thumbnails (`app-overview-after.png`)

One sentence under the video is worth adding for Qlik Sense administrators: the dry run lists **every** sheet in the app, including sheets hidden behind show conditions — the hub never displays those, so the plan showing one is the quickest proof the tool reads the app itself rather than scraping the hub.
